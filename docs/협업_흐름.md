# GitHub 협업 흐름 (처음인 사람용)

## 비유: 팀 공용 보고서를 같이 고친다
| 용어 | 비유 | 실제 |
| --- | --- | --- |
| **main** | 팀 공용 **최종본** | 항상 잘 돌아가는 완성본. 직접 고치지 않음 |
| **브랜치 파기** | 최종본을 **"사본 만들기"** | `git switch -c feat/작업이름` — 내 작업 공간 |
| **커밋** | 사본에서 **저장 지점** 찍기 (게임 세이브) | `git add` → `git commit -m "..."` 여러 번 해도 됨 |
| **push** | 내 사본을 GitHub에 **올려두기** (백업 겸) | `git push -u origin feat/작업이름` |
| **PR (Pull Request)** | **"제 사본을 최종본에 반영해도 될까요?" 결재 요청서** | GitHub에서 여는 검토 페이지 |
| **Merge** | 결재 승인 → **최종본에 실제 반영** | PR 페이지의 **Squash and merge** 버튼 |

> PR ≠ Merge. **PR은 요청서**, **Merge는 그 요청서에서 승인해서 합치는 동작**.

```
main (최종본)  ●─────────────────────●  ← ④ Merge (합쳐짐)
                \                    /
 내 브랜치(사본)  ●── 커밋 ── 커밋 ──●
             ① 사본 만들기  ② 작업·저장   ③ PR 열기 (자동 검사 + 팀원 확인)
```

**Squash merge**: 사본에서 커밋을 10번 했어도 최종본엔 "편성표 화면 추가" **한 줄로 묶어서** 반영 → main 기록이 깔끔.

## 왜 이렇게 하나
- 여럿이 최종본을 직접 고치면 서로 덮어써서 꼬임
- 사본에서 작업하면 최종본은 항상 안전, 합치기 전 검사·확인 한 번
- 잘못되면 그 브랜치만 버리면 끝

## 실제 순서 (매번 이것만 반복)
| 단계 | 명령 / 동작 |
| --- | --- |
| 0. 최신 최종본 받기 | `git switch main` → `git pull` |
| 1. 사본 만들기 | `git switch -c engine/scoring` (할 일은 먼저 GitHub 이슈로) |
| 2. 작업 + 저장 | 파일 수정 → `git add .` → `git commit -m "feat: 점수 계산"` |
| 3. 올리기 | `git push -u origin engine/scoring` |
| 4. PR 열기 | GitHub 저장소 페이지의 **Compare & pull request** → 무엇을/왜 + `Closes #이슈번호` → Create |
| 5. 확인 | 자동 검사 초록불 확인 (Checks 가 0 이면 **Update branch** 먼저). 공통 폴더를 바꾼 PR만 3명 확인 |
| 6. 합치기 | **본인이** Squash and merge → Confirm (브랜치는 자동 삭제) |
| 7. 내 컴퓨터 정리 | `git switch main` → `git pull` |

## 브랜치 이름
`영역/내용` — 영역: `data`(A) · `engine`(B) · `tv`·`voice`(C) · `family`(A) · `common`(공통) (예: `engine/scoring`, `tv/popup`)

## 꼭 지킬 약속
1. main에서 바로 작업·커밋 안 함 (훅이 막아줌)
2. **자기 폴더만** 고침. 공통 폴더(`models/`, `contracts/`, `main.py`, `data/sample/`, `docs/`)는 3명 동의할 때만
3. 브랜치는 1~2일 안에 PR → 합치기. 길어지면 쪼개기
4. 본인 PR은 본인이 합친다. 단 공통 폴더 변경은 3명 확인 후 (API를 추가만 했으면 단톡 알림)
5. 빨간불(검사 실패) PR은 합치지 않기
6. API 키는 `backend/.env` 에만
