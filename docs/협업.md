# 협업 (팀원 · Git 흐름 · 응급처치)

규칙 원본은 `AGENTS.md`. 이 문서는 사람용 쉬운 설명.

## 비유: 팀 공용 보고서를 같이 고친다
| 용어 | 비유 | 실제 |
| --- | --- | --- |
| **main** | 팀 공용 **최종본** | 항상 잘 돌아가는 완성본. 직접 고치지 않음 |
| **브랜치 파기** | 최종본을 **"사본 만들기"** | `git switch -c engine/scoring` — 내 작업 공간 |
| **커밋** | 사본에서 **저장 지점** 찍기 (게임 세이브) | `git add` → `git commit -m "..."` 여러 번 해도 됨 |
| **push** | 내 사본을 GitHub에 **올려두기** (백업 겸) | `git push -u origin engine/scoring` |
| **PR (Pull Request)** | **"제 사본을 최종본에 반영해도 될까요?" 결재 요청서** | GitHub에서 여는 검토 페이지 |
| **Merge** | 결재 승인 → **최종본에 실제 반영** | PR 페이지의 **Squash and merge** 버튼 |

> PR ≠ Merge. **PR은 요청서**, **Merge는 그 요청서에서 승인해서 합치는 동작**.

```
main (최종본)  ●─────────────────────●  ← ④ Merge (합쳐짐)
                \                    /
 내 브랜치(사본)  ●── 커밋 ── 커밋 ──●
             ① 사본 만들기  ② 작업·저장   ③ PR 열기 (자동 검사 + 팀원 확인)
```

**Squash merge**: 사본에서 커밋을 10번 했어도 최종본엔 "편성표 화면 추가" **한 줄로 묶어서** 반영 → main 기록이 깔끔.

## 왜 이렇게 하나
- 여럿이 최종본을 직접 고치면 서로 덮어써서 꼬임
- 사본에서 작업하면 최종본은 항상 안전, 합치기 전 검사·확인 한 번
- 잘못되면 그 브랜치만 버리면 끝

## 실제 순서 (매번 이것만 반복)
| 단계 | 명령 / 동작 |
| --- | --- |
| 0. 최신 최종본 받기 | `git switch main` → `git pull` |
| 1. 사본 만들기 | `git switch -c engine/scoring` (할 일은 먼저 GitHub 이슈로) |
| 2. 작업 + 저장 | 파일 수정 → `git add .` → `git commit -m "feat: 점수 계산"` |
| 3. 올리기 | `git push -u origin engine/scoring` |
| 4. PR 열기 | GitHub 저장소 페이지의 **Compare & pull request** → 무엇을/왜 + `Closes #이슈번호` → Create |
| 5. 확인 | 자동 검사 초록불 확인 (Checks 가 0 이면 **Update branch** 먼저). 공통 폴더를 바꾼 PR만 3명 확인 |
| 6. 합치기 | **본인이** Squash and merge → Confirm (브랜치는 자동 삭제) |
| 7. 내 컴퓨터 정리 | `git switch main` → `git pull` |

## 브랜치 이름
`영역/내용` — 영역: `data`(A) · `engine`(B) · `tv`·`voice`(C) · `family`(A) · `common`(공통) (예: `engine/scoring`, `tv/popup`)

## 꼭 지킬 약속
1. main에서 바로 작업·커밋 안 함 (훅이 막아줌)
2. **자기 폴더만** 고침. 공통 폴더(`models/`, `contracts/`, `main.py`, `data/sample/`, `docs/`)는 3명 동의할 때만
3. 브랜치는 1~2일 안에 PR → 합치기. 길어지면 쪼개기
4. 본인 PR은 본인이 합친다. 단 공통 폴더 변경은 3명 확인 후 (API를 추가만 했으면 단톡 알림)
5. 빨간불(검사 실패) PR은 합치지 않기
6. API 키는 `backend/.env` 에만

## 꼬였을 때 응급처치
### 우리 저장소의 안전장치
| 장치 | 막아주는 것 |
| --- | --- |
| `pnpm install` 하면 자동 설치되는 Git 훅 | main 에서 바로 커밋 · main 에 직접 push · `.env`·API 키 커밋 |
| GitHub 설정 | 합치기는 **Squash만** 가능 · 합친 브랜치 자동 삭제 · PR에 "최신 main 반영" 버튼 표시 |
| 자동 검사(CI) | PR마다 백엔드·프론트·계약 검사. **빨간불이면 합치지 않기** |
| 폴더 분담 | 각자 자기 폴더만 고치니 같은 파일을 동시에 고칠 일이 거의 없음 |

> 리뷰는 필수 아님: CI 초록불이면 본인이 합친다. 공통 폴더 변경만 3명 확인.

### 상황별 해결
| 상황 | 해결 |
| --- | --- |
| main 에서 작업해버림 (커밋 전) | `git switch -c 영역/내용` → 고친 내용 그대로 새 브랜치로 따라감 |
| main 에서 커밋까지 해버림 | `git switch -c 영역/내용` → `git switch main` → `git reset --hard origin/main` → `git switch 영역/내용` |
| PR에 "This branch has conflicts" | 혼자 고치지 말고 단톡에 PR 링크 공유. 보통 `contracts/` 나 공용 파일 문제 → 백엔드 담당이 해결 |
| PR에 "out-of-date with main" | PR 화면의 **Update branch** 버튼 클릭 |
| 내 컴퓨터가 이상해짐, 처음부터 다시 | 작업 중인 파일 따로 백업 → `git fetch` → `git switch main` → `git reset --hard origin/main` |
| 실수로 API 키를 올림 | **즉시** 해당 서비스에서 키 폐기·재발급 (Git에서 지워도 기록에 남음) → 단톡 공유 |
| 뭐가 뭔지 모르겠음 | `git status` 결과를 통째로 복사해서 단톡이나 Claude/Codex에 질문 |

### 하루 시작·끝 습관
- 시작: `git switch main && git pull` → 새 브랜치
- 끝: 커밋하고 `git push` (완성 안 됐어도 내 브랜치엔 올려두기 = 백업)
