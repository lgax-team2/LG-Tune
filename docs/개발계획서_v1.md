## 0. 개발 원칙 5개

| # | 원칙 | 구체적으로 |
| --- | --- | --- |
| 1 | **계약 먼저 (Contract-first)** | REST(OpenAPI)·WebSocket 이벤트 스키마를 1일차에 고정하고 저장소에 커밋. 프론트·백엔드는 계약만 보고 동시에 개발 |
| 2 | **목업으로 분리** | 프론트는 목업 서버(시나리오 재생기)로 개발 → 백엔드 진도와 무관하게 화면 완성 |
| 3 | **얇은 끝까지 흐름 먼저 (Vertical slice)** | 1주차 안에 "시계 → 편성 → 말하기 → 응/아니 → 채널 전환 → 지표"를 가짜 부품으로라도 끝까지 연결. 이후 부품을 진짜로 교체 |
| 4 | **어댑터 뒤에 숨기기** | LLM·STT·TTS·재생 제어는 인터페이스 + 가짜 구현 + 진짜 구현. 환경 변수로 교체 |
| 5 | **시나리오 재생 테스트** | 시연 시나리오(하루치 시계 + 가짜 음성 입력)를 자동 테스트로 만들어 매 PR마다 실행. 리허설 = 테스트 통과 |

## 2. 저장소와 GitHub 운영

### 2.1 저장소: 모노레포 1개 (`lg-tune`, private)
모노레포를 고르는 이유: 계약 파일이 한 곳에 있어 백엔드·프론트가 어긋날 수 없고, PR 하나로 계약과 구현을 같이 바꿀 수 있음. 팀 규모(4~5명)에서는 저장소를 나눌 이득이 없음.

```
lg-tune/
├ .github/
│  ├ workflows/ (ci-backend.yml, ci-frontend.yml, ci-contracts.yml)
│  ├ CODEOWNERS
│  └ pull_request_template.md

│  ├ openapi.json            (FastAPI에서 자동 생성, 커밋)
│  ├ ws-events.schema.json   (Pydantic 모델에서 자동 생성, 커밋)
│  └ scenarios/              (시연 시나리오: 시간별 이벤트 스크립트 .jsonl)

│  ├ app/ (main.py, settings.py, api/, ws/, clock/, plan/, voice/, dialogue/,
│  │       memory/, modules/, llm/, tts/, metrics/, db/)
│  ├ adapters/ (playback/, llm/, stt/, tts/ — 각각 fake.py + real.py)
│  ├ tests/ (unit/, contract/, scenario/)
│  └ pyproject.toml, uv.lock
├ frontend/
│  ├ src/ (tv/, setup/, dashboard/, shared/api/ ← 계약에서 생성된 타입)

├ ml/
│  ├ wakeword/ (데이터 생성·학습·평가 노트북과 스크립트)

│  └ stt_lora/
├ models/manifest.json       ← 모델 파일 목록·버전·sha256 (파일 자체는 Git 밖)
```

## 3. 프론트와 백엔드를 어떻게 분리해서 개발하나

### 3.1 분리의 핵심: 계약 + 타입 자동 생성 + 목업
```
[백엔드 Pydantic 모델] ──(스크립트)──▶ contracts/openapi.json
                    └─(스크립트)──▶ contracts/ws-events.schema.json
                                            │
                              (pnpm gen:types)
                                            ▼
                           frontend/src/shared/api/*.ts (타입 자동 생성)
```
- 백엔드가 이벤트 모양을 바꾸면 계약 파일이 바뀌고 → 프론트 타입이 바뀌어 → **프론트 빌드가 깨져서 바로 알 수 있음**
- CI의 `contracts` 작업: 계약을 다시 생성해서 커밋된 파일과 다르면 실패 (누가 계약을 몰래 바꾸는 것 방지)
- 도구: OpenAPI → `openapi-typescript`, JSON Schema → `json-schema-to-typescript`

### 3.2 프론트 목업 (백엔드 없이 화면 개발)
| 목업 | 내용 |
| --- | --- |
| REST | MSW(Mock Service Worker)로 설정·편성 조회 응답 |
| WebSocket | `mock/ws-replay.ts`: `contracts/scenarios/day1.jsonl`을 시간 순서대로 재생하는 작은 서버. 속도 배속 옵션 |
| 시나리오 파일 | 백엔드 시나리오 테스트와 **같은 파일**을 씀 → 프론트·백엔드가 같은 장면을 기준으로 개발 |

### 3.3 WebSocket 이벤트 (v1 초안, 1일차에 확정)
모든 메시지 공통: `{ "v": 1, "type": "...", "ts": "ISO8601", "id": "uuid", "data": {...} }`

| 방향 | type | data | 화면 동작 |
| --- | --- | --- | --- |
| 서버→화면 | `plan.updated` | 오늘 편성 항목 목록(시간, 프로그램, 고른 이유, 상태) | 편성표 오버레이 갱신 |
| | `buddy.say` | 문장, 음성 URL, 표시 시간, 말투 | 말풍선 + 음성 재생 |
| | `listen.open` / `listen.close` | 듣기 창 ID, 제한 시간 | 듣는 중 표시 |
| | `asr.partial` / `asr.final` | 인식 글자 | (선택) 자막처럼 표시 |
| | `playback.switch` | 채널, 프로그램, 시작 위치 | 플레이어 채널 전환 |
| | `card.show` | 종류(인물관계도/구절/공연), 내용 | 카드 표시 |
| | `card.hide` | 카드 ID | 카드 닫기 |
| | `clock.tick` | 시연 시각, 배속 | 화면 시계 |
| | `metrics.snapshot` | 지표 묶음 | 대시보드 |
| 화면→서버 | `player.state` | 채널, 재생 위치, 광고 구간 여부 | 서버가 "지금 말해도 되나" 판단 |
| | `remote.press` | 버튼(확인/취소/채널±) | 2단계 개입, 직접 조작 감지 |
| | `ui.ready` | 화면 준비 완료 | 서버가 상태 재전송 |

### 3.4 REST API (v1 초안)
| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| POST | `/api/setup` | 자녀 폰 첫 설정 저장 |
| GET | `/api/plan/today` | 오늘 편성 |
| GET | `/api/plan/{date}` | 날짜별 편성 (1일차 vs 7일차 비교 화면) |
| GET | `/api/epg?date=` | 가상 EPG |
| GET | `/api/metrics` | 지표 집계 |
| POST | `/api/demo/clock` | 시연 시계 이동·배속 (데모 모드에서만) |
| POST | `/api/demo/inject` | 가짜 음성 입력 주입 (테스트·리허설용, 데모 모드에서만) |
| GET | `/healthz` | 상태 점검 (LLM·STT·DB 상태 포함) |

### 3.5 화면 개발 순서 (프론트)
1. TV 셸 + 가상 채널 플레이어(영상 + .vtt 자막 + 광고 구간 표시)
2. 편성표 오버레이 (어르신용: 큰 글씨, 고대비, 한 화면에 3~5칸)
3. 단짝 말풍선 + 듣는 중 표시
4. 카드 3종 (인물 관계도, 구절, 공연)
5. 자녀 설정 페이지 (모바일)
6. 1일차/7일차 비교 화면 + 지표 대시보드

## 4. 개발 환경

### 4.1 공통 (Windows 11 기준)
| 도구 | 버전·선택 | 이유 |
| --- | --- | --- |
| Git + GitHub | private 저장소 | |
| Python | 3.11, **uv**로 가상환경·잠금 | 설치가 빠르고 팀원 간 버전이 어긋나지 않음 |
| Node | 20 LTS, **pnpm** | |
| 편집기 | VS Code + 권장 확장(.vscode/extensions.json) | |
| 작업 실행 | 루트 `package.json` 스크립트 또는 `scripts/*.ps1` | Windows에서 make 없이 한 줄 실행 |
| 비밀값 | `backend/.env` (예시는 `.env.example`) | Git 제외 |

### 4.2 실행 프로필 (환경 변수로 전환)
| 프로필 | LLM | STT | TTS | 재생 | 시계 | 용도 |
| --- | --- | --- | --- | --- | --- | --- |
| `dev` | 가짜(정해진 문장) 또는 진짜 | 가짜(텍스트 입력) | 가짜(무음) | 가상 | 실제 시간 | 일상 개발 |
| `test` | 가짜 | 가짜 | 가짜 | 가짜 | 조작 가능 | CI·시나리오 테스트 |
| `demo` | 진짜 + 예비 | 진짜 | 진짜 + 캐시 | 가상 | 배속 가능 | 리허설·촬영·발표 |

설정은 `pydantic-settings` 하나로 관리: `LLM_PROVIDER`, `STT_PROVIDER`, `TTS_PROVIDER`, `PLAYBACK`, `CLOCK_SPEED`, `DEMO_MODE`.

### 4.3 한 줄 실행
```
pnpm dev        # 백엔드(uvicorn --reload) + 프론트(vite) 동시 실행
pnpm dev:fe     # 프론트 + 목업 서버만 (백엔드 없이)
pnpm test       # 백엔드 pytest + 프론트 vitest
pnpm gen        # 계약 재생성 + 프론트 타입 생성
pnpm demo       # 프론트 빌드 → FastAPI가 정적 파일 제공 → 브라우저 전체화면
```

### 4.4 Docker를 쓰나?
**기본은 안 씀.** 마이크·오디오 장치 접근과 Windows 환경 때문에 컨테이너가 오히려 걸림돌. 대신 `uv.lock`·`pnpm-lock.yaml`로 재현성을 확보. (제품 단계 서버 부분만 나중에 컨테이너화)

## 6. 테스트 전략

| 층 | 대상 | 예 |
| --- | --- | --- |
| 단위 | 편성 점수, 하드 규칙, 밴딧 갱신, 기억 검색 점수, 꺼내기 빈도 제한, 응/아니 후처리 규칙 | "취침 30분 전 프로그램은 편성에 안 들어간다" |
| 계약 | 서버가 보내는 모든 WS 메시지가 스키마에 맞는가 | 스키마 검증 |
| 시나리오 | `scenarios/*.jsonl`을 시계와 함께 재생 → 기대 이벤트 순서 검증 | "19:50 알림 → '아니' → 20:00 전환 없음 → 반응 기록" |
| 장애 주입 | LLM 타임아웃, 네트워크 끊김, STT 실패 | "Claude 실패 → 3초 내 예비 모델 → 고정 멘트" |
| 성능 | 말 끝 → 첫 소리 지연 | p95 3초 초과 시 실패 표시 |
| ML 평가 | 각 모델의 고정 평가셋 | 호출어 FPPH·재현율, 분류기 F1, STT CER |
| 리허설 | 실제 마이크·노트북으로 시연 대본 3회 연속 통과 | 체크리스트 |

**테스트 먼저(TDD) 적용 범위:** 편성 엔진, 기억 점수, 꺼내기 규칙, 듣기 창 규칙. 틀리면 시연이 망가지는 순수 로직이라 테스트 비용 대비 효과가 가장 큼.

## 7. ML 작업 흐름

| 단계 | 방법 |
| --- | --- |
| 실험 환경 | Colab 유료 GPU (학교 지원), `ml/<모델>/train.ipynb` + `eval.py` |
| 데이터 | 원본은 Git 밖(구글 드라이브 팀 폴더). 저장소에는 생성 스크립트와 데이터 카드만 |
| 산출물 | ONNX로 내보내기 → GitHub Releases(private)에 업로드 |
| 버전 관리 | `models/manifest.json`: `{name, version, url, sha256, metrics, date}`. 백엔드는 시작할 때 해시 확인 후 로드 |
| 평가 고정 | 평가셋은 처음에 고정하고 바꾸지 않음 → 버전 간 비교 가능 |
| 모델 카드 | 각 모델 폴더에 `MODEL_CARD.md`: 데이터, 학습 설정, 평가 수치, 한계 |

## 10. AI 코딩 도구 사용 규칙 (Claude Code / Codex)
병렬 사용 방식은 개발 시작 때 따로 토의(보류 항목). 다만 지금 정할 공통 규칙:

| 규칙 | 내용 |
| --- | --- |
| 규칙 파일 | `CLAUDE.md`(Claude Code), `AGENTS.md`(Codex)에 같은 내용: 폴더 구조, 실행 명령, 계약 파일 위치, "계약은 사람 승인 없이 바꾸지 말 것", 테스트 먼저 범위 |
| 작업 단위 | 이슈 1개 = 브랜치 1개 = AI 세션 1개. 같은 파일을 두 도구가 동시에 고치지 않음 |
| 검증 | AI가 만든 코드도 CI·리뷰 동일 적용. 특히 편성·기억 로직은 사람이 테스트 케이스를 먼저 씀 |
| 비밀값 | API 키를 프롬프트·코드에 붙여 넣지 않음. `.env`만 |
